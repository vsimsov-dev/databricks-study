Day 2 · Delta Lake

Delta Lake 기초

신뢰할 수 있는 데이터 저장의 비밀

⏱ 학습 시간: 약 10분 📝 퀴즈: 5문제 🔄 복습: 4문제
개념 설명

왜 Delta Lake가 필요한가?

데이터를 파일로 저장하는 건 간단해 보이지만, 실제 업무에서는 문제가 생깁니다. 분석팀이 파일을 읽는 도중 다른 팀이 같은 파일을 덮어쓰면 어떻게 될까요? 파이프라인이 절반만 실행되다 오류로 멈추면, 데이터가 반만 쓰인 채 남겨집니다. 수백만 건의 데이터 중 어떤 건이 가장 최신인지 알 수 없는 상황도 발생합니다. 이런 문제들이 데이터 레이크의 고질적인 한계였습니다.

Delta Lake는 이 문제를 해결하기 위해 만들어진 오픈소스 스토리지 레이어입니다. Parquet 파일 위에 트랜잭션 로그(_delta_log)를 덧씌워, 데이터베이스처럼 신뢰할 수 있는 읽기·쓰기를 가능하게 합니다.

핵심 개념: ACID 트랜잭션

Delta Lake가 제공하는 가장 중요한 특성은 ACID 트랜잭션입니다. 원래 데이터베이스 세계의 개념인데, Delta Lake가 이걸 데이터 레이크에 가져왔습니다.

⚛️

Atomicity (원자성)

쓰기 작업은 전부 성공하거나 전부 실패합니다. 절반만 쓰인 데이터는 없습니다.

✅

Consistency (일관성)

데이터는 항상 정의된 스키마와 규칙을 지킵니다. 엉뚱한 타입이 들어올 수 없습니다.

🔒

Isolation (격리성)

동시에 여러 작업이 실행돼도 서로 간섭하지 않습니다. 읽는 도중 쓰기가 방해하지 않습니다.

💾

Durability (지속성)

완료된 트랜잭션은 시스템 오류가 나도 사라지지 않습니다. 기록은 영구 보존됩니다.

Time Travel — 시간을 되돌리는 능력

Delta Lake의 또 다른 강력한 기능은 Time Travel입니다. _delta_log에는 모든 변경 이력이 버전으로 남아있기 때문에, 과거 특정 시점의 데이터를 조회할 수 있습니다. 예를 들어 "어제 오전 10시 기준 데이터"나 "3번 버전 이전 데이터"를 그대로 읽어올 수 있습니다.

💡 SQL로 Time Travel 하는 법 -- 버전으로 조회
SELECT * FROM my_table VERSION AS OF 3;

-- 타임스탬프로 조회
SELECT * FROM my_table TIMESTAMP AS OF '2026-06-01 10:00:00';

Schema Evolution — 스키마가 바뀌어도 괜찮아

업무를 하다 보면 데이터 구조가 바뀌는 건 피할 수 없습니다. 고분자 제품 분석 데이터에 새로운 측정 항목이 추가되는 경우처럼요. Delta Lake는 Schema Evolution(스키마 진화)을 지원해서, 기존 데이터를 건드리지 않고도 컬럼을 추가하거나 변경할 수 있습니다. 반대로 의도치 않은 스키마 변경을 막는 Schema Enforcement(스키마 강제)도 기본으로 켜져 있습니다.

기존 방식과의 비교

❌ 일반 데이터 레이크 (Parquet만)
  • 파이프라인 실패 시 데이터 손상
  • 동시 읽기·쓰기 충돌 발생
  • 과거 데이터 복구 불가
  • 스키마 오류 감지 어려움
  • UPDATE/DELETE 지원 안 됨
✅ Delta Lake
  • ACID 트랜잭션으로 안전 보장
  • 동시 작업 격리 처리
  • Time Travel로 과거 버전 조회
  • Schema Enforcement 자동 적용
  • MERGE/UPDATE/DELETE 지원

팀에서는 어떻게 활용하나요?

고분자 제품 개발 업무에서 생산 공정 데이터나 물성 측정 데이터를 수집할 때, 기존 방식은 CSV나 Excel 파일을 날짜별로 쌓아두는 방식이었을 겁니다. 이러면 같은 날짜 파일이 두 버전으로 존재하거나, 업데이트 도중 파일이 깨지는 문제가 생길 수 있습니다.

Databricks에서 Delta Lake 테이블로 데이터를 관리하면, 팀에서 누가 언제 어떤 데이터를 수정했는지 이력이 남고, 실수로 잘못된 데이터를 넣었을 때 이전 버전으로 바로 되돌릴 수 있습니다. 특히 배터리 파우치용 CPP나 압출코팅 PP 공정 데이터처럼 시간에 따른 변화 추적이 중요한 데이터에 Delta Lake가 매우 유용합니다.

오늘의 퀴즈
1Delta Lake가 기존 Parquet 저장 방식과 가장 크게 다른 점은 무엇인가요?
✅ 정답: ②
Delta Lake는 Parquet 파일 위에 _delta_log라는 트랜잭션 로그를 추가해 ACID 속성을 보장합니다. 데이터 자체는 여전히 컬럼형 Parquet 포맷으로 저장됩니다.
2ACID의 'A'인 Atomicity(원자성)를 가장 잘 설명한 것은?
✅ 정답: ③
원자성은 트랜잭션이 '전부 아니면 전무(All or Nothing)'로 처리됨을 의미합니다. 파이프라인이 중간에 실패해도 절반만 쓰인 데이터가 남지 않습니다.
3Delta Lake의 Time Travel 기능으로 할 수 있는 것은?
✅ 정답: ①
Time Travel은 _delta_log에 남겨진 버전 이력을 이용해 과거 특정 시점 또는 버전 번호 기준으로 데이터를 조회하거나 복원할 수 있습니다.
4Delta Lake의 Schema Enforcement 기능은 어떤 역할을 하나요?
✅ 정답: ④
Schema Enforcement는 테이블에 정의된 스키마와 다른 구조의 데이터가 들어오려 하면 에러를 발생시켜 잘못된 데이터 유입을 막습니다. 이는 Schema Evolution(의도적 스키마 변경)과 구별됩니다.
5Delta Lake에서 _delta_log에 저장되는 것은?
✅ 정답: ②
_delta_log 폴더에는 INSERT, UPDATE, DELETE, MERGE 등 테이블에 가해진 모든 변경 작업이 JSON 파일로 버전별 기록됩니다. 실제 데이터는 Parquet 파일에 저장됩니다.
어제 배운 내용 복습 — Day 1: Databricks와 레이크하우스 개념
1데이터 웨어하우스, 데이터 레이크, 레이크하우스에 대한 설명으로 옳은 것은?
✅ 정답: ③
레이크하우스는 데이터 레이크(유연성·저비용)와 웨어하우스(속도·신뢰성)의 장점을 결합한 구조입니다. 웨어하우스는 정형 데이터만, 레이크는 모든 형식을 저장할 수 있으며, 웨어하우스는 비용이 가장 비쌉니다.
2Databricks가 "레이크하우스 플랫폼"으로 불리는 가장 핵심적인 이유는?
✅ 정답: ②
Databricks는 S3·ADLS 같은 오브젝트 스토리지(데이터 레이크)를 기반으로 하면서, Delta Lake 기술로 웨어하우스 수준의 신뢰성과 성능을 제공합니다. 덕분에 하나의 플랫폼에서 데이터 엔지니어링, BI 분석, ML/AI를 모두 처리할 수 있어 레이크하우스 플랫폼이라 불립니다.
3기존 데이터 사일로(사업부별 Excel/CSV 관리) 방식의 문제점이 아닌 것은?
✅ 정답: ④
사일로 방식에서는 각 부서가 데이터를 따로 관리하기 때문에 오히려 중복 작업이 많이 발생합니다. 같은 데이터를 여러 팀이 각자 가공해 공수가 낭비되는 것이 핵심 문제 중 하나입니다.
4레이크하우스에서 BI 분석과 ML 학습이 같은 데이터 소스를 공유할 때 얻는 핵심 장점은?
✅ 정답: ①
BI 팀과 ML 팀이 동일한 데이터 소스를 사용하면 데이터 복사·이동 비용이 없어지고, 분석 결과와 모델 학습 데이터 간 불일치가 사라집니다. 또한 데이터 거버넌스를 한 곳에서 관리하고, ML 모델이 실제 BI와 동일한 최신 데이터로 학습되어 신뢰도가 높아집니다.
5Delta Lake에서 모든 변경 이력을 JSON으로 기록하는 폴더의 이름은 무엇인가요?
정답: _delta_log
Delta 테이블 폴더 안에 생성되는 디렉터리로, INSERT·UPDATE·DELETE 등 모든 변경 작업을 버전별 JSON 파일로 기록합니다. Time Travel과 ACID 트랜잭션의 핵심 기반입니다.

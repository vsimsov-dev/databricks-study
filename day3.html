Unity Catalog 구조

데이터를 체계적으로 관리하는 3단계 계층 구조

⏱ 학습 시간: 약 10분 📝 퀴즈: 5문제 🔄 복습: 4문제
개념 설명

Unity Catalog이란?

데이터가 많아질수록 "이 테이블이 어디 있지?", "이 데이터를 누가 볼 수 있지?" 같은 질문이 생깁니다. Databricks에서는 Unity Catalog이 이 문제를 해결합니다. Unity Catalog은 Databricks 플랫폼 전체의 데이터 자산을 한 곳에서 관리하는 통합 거버넌스 레이어입니다. 테이블, 뷰, 파일, 모델까지 모두 등록하고, 누가 어떤 데이터에 접근할 수 있는지 권한을 중앙에서 제어합니다.

3단계 계층 구조: Catalog > Schema > Table

Unity Catalog의 핵심은 3단계 네임스페이스(namespace)입니다. 마치 회사 파일 서버에서 "부서 폴더 → 프로젝트 폴더 → 파일" 구조로 관리하는 것과 같습니다.

🗂️
Catalog (카탈로그) — 최상위 컨테이너. 보통 사업 단위 또는 환경(dev/prod)으로 구분.
예: polymer_tech, sales, dev_catalog
↓ 포함
📁
Schema (스키마) — 카탈로그 안의 중간 폴더. 주제 또는 팀 단위로 구분.
예: film_quality, customer_support, raw_data
↓ 포함
📋
Table / View (테이블/뷰) — 실제 데이터가 담긴 단위.
예: thickness_measurements, defect_images
💡 3단계 주소로 데이터 접근하기 Unity Catalog에서 테이블은 아래처럼 점(.)으로 연결된 3단계 이름으로 접근합니다.
-- catalog.schema.table 형식
SELECT * FROM polymer_tech.film_quality.thickness_measurements;

-- 현재 catalog/schema 설정 후 단축 접근도 가능
USE CATALOG polymer_tech;
USE SCHEMA film_quality;
SELECT * FROM thickness_measurements;

Unity Catalog의 핵심 기능

🔐

중앙 권한 관리 (Fine-grained Access Control)

카탈로그·스키마·테이블·컬럼 단위로 누가 읽고 쓸 수 있는지 한 곳에서 제어합니다. 컬럼 마스킹으로 민감 데이터는 숨길 수도 있습니다.

🔍

데이터 탐색 (Data Discovery)

등록된 모든 테이블을 검색하고, 각 테이블의 설명·소유자·태그를 확인할 수 있습니다. "이 데이터가 어디 있지?"를 빠르게 해결합니다.

🗺️

데이터 리니지 (Data Lineage)

특정 테이블이 어떤 원본 데이터에서 만들어졌는지, 그 테이블로 어떤 다운스트림 테이블이 만들어지는지 계보를 시각화합니다.

📊

감사 로그 (Audit Log)

누가 언제 어떤 데이터에 접근했는지 자동으로 기록됩니다. 보안 감사나 규정 준수에 필수적인 기능입니다.

권한(Permission) 구조

Unity Catalog의 권한은 계층적으로 상속됩니다. 상위 레벨(카탈로그)에 권한을 부여하면 하위(스키마, 테이블)에도 자동으로 적용됩니다. 반대로 하위 레벨에만 특정 권한을 주는 것도 가능합니다.

권한 레벨 대표 권한 설명
Catalog USE CATALOG, CREATE SCHEMA 카탈로그 전체 접근. 하위 모든 스키마·테이블에 상속됨.
Schema USE SCHEMA, CREATE TABLE 해당 스키마 안의 테이블 접근·생성 권한.
Table SELECT, MODIFY 특정 테이블만 읽기(SELECT) 또는 수정(MODIFY) 권한.
💡 권한 부여 SQL 예시 -- 그룹에 카탈로그 접근 권한 부여
GRANT USE CATALOG ON CATALOG polymer_tech TO `data_team`;

-- 특정 테이블 읽기 권한만 부여
GRANT SELECT ON TABLE polymer_tech.film_quality.thickness_measurements TO `analyst_group`;

기존 방식과의 비교

❌ Unity Catalog 없이
  • 팀마다 데이터가 따로 흩어져 있음
  • 권한 관리가 워크스페이스별로 분리됨
  • 어떤 테이블이 있는지 파악 불가
  • 데이터 출처 추적이 어려움
  • 컬럼 단위 보안 적용 불가
✅ Unity Catalog 사용 시
  • 하나의 카탈로그에서 전사 데이터 관리
  • 중앙 권한 관리, 워크스페이스 간 공유
  • 검색·태그로 데이터 빠르게 탐색
  • 리니지로 데이터 흐름 시각화
  • 컬럼·행 단위 세밀한 보안 적용

고분자제품기술팀에서는 이렇게 쓸 수 있어요

팀에서 Unity Catalog을 활용한다면 이런 구조를 생각해볼 수 있습니다.
Catalog: polymer_tech (팀 전체 데이터)
Schema: film_quality, rd_experiments, customer_support
Table: thickness_data, tensile_strength, defect_log, tds_specs

예를 들어 PP TDS 챗봇을 만든다면 polymer_tech.tds.pp_grades처럼 명확한 3단계 주소로 관리하고, 분석팀에는 SELECT만, 개발팀에는 CREATE TABLE까지 부여하는 식으로 역할별 권한을 정교하게 분리할 수 있습니다.

핵심 용어 카드

Unity Catalog
Databricks의 통합 데이터 거버넌스 레이어. 데이터 자산 관리·권한·리니지를 한 곳에서 처리.
Catalog
3단계 계층의 최상위. 사업 단위나 환경(dev/prod)으로 구분하는 최대 컨테이너.
Schema
카탈로그 안의 중간 폴더. 주제 또는 팀 단위로 테이블을 묶는 논리적 단위.
Data Lineage
데이터의 출처부터 하류까지 흐름을 추적하는 계보. 오류 원인 파악에 핵심.
Fine-grained Access
컬럼·행 단위까지 세밀하게 권한을 나누는 접근 제어 방식.

오늘의 퀴즈
1Unity Catalog의 3단계 계층 구조를 올바른 순서로 나열한 것은?
✅ 정답: ③
Unity Catalog는 최상위 Catalog, 그 안에 Schema, 그 안에 Table(또는 View) 순서의 3단계 계층 구조를 사용합니다. SQL로 접근할 때는 catalog.schema.table 형식을 사용합니다.
2Unity Catalog에서 Data Lineage 기능이 제공하는 것은?
✅ 정답: ②
Data Lineage(데이터 리니지)는 데이터의 출처(업스트림)부터 파생된 테이블(다운스트림)까지 흐름을 시각화합니다. 오류가 발생했을 때 원인 데이터를 빠르게 추적하고, 변경 영향도를 파악하는 데 핵심 기능입니다.
3Unity Catalog에서 권한이 계층적으로 상속된다는 것은 무엇을 의미하나요?
✅ 정답: ①
Unity Catalog의 권한은 상위 레벨에서 하위로 상속됩니다. 예를 들어 USE CATALOG 권한을 부여하면 그 카탈로그 안의 모든 스키마·테이블에도 접근 권한이 내려갑니다. 단, 하위 레벨에서 더 세밀한 제어를 추가하는 것도 가능합니다.
4polymer_tech.film_quality.thickness_measurements에서 film_quality에 해당하는 계층은?
✅ 정답: ④
catalog.schema.table 형식에서 가운데에 위치한 film_quality는 Schema(스키마)입니다. polymer_tech가 Catalog, thickness_measurements가 Table에 해당합니다.
5Unity Catalog의 감사 로그(Audit Log) 기능으로 확인할 수 있는 것은?
✅ 정답: ③
Unity Catalog의 감사 로그는 사용자가 언제, 어떤 테이블에, 어떤 쿼리로 접근했는지를 자동으로 기록합니다. 보안 감사, GDPR·데이터 규정 준수, 이상 접근 탐지에 활용됩니다.
어제 배운 내용 복습 — Day 2: Delta Lake 기초
1Delta Lake가 일반 Parquet 저장 방식과 다른 핵심 차이점은?
✅ 정답: ②
Delta Lake는 Parquet 파일 위에 _delta_log라는 트랜잭션 로그를 덧씌워 ACID(원자성·일관성·격리성·지속성) 속성을 보장합니다. 데이터 자체는 여전히 컬럼형 Parquet 포맷으로 저장됩니다.
2Delta Lake의 Time Travel을 사용하는 SQL 문법으로 올바른 것은?
✅ 정답: ③
Delta Lake의 Time Travel은 VERSION AS OF [버전번호] 또는 TIMESTAMP AS OF '[타임스탬프]' 구문을 사용합니다. ROLLBACK, HISTORY, WHERE 구문은 Time Travel 문법이 아닙니다.
3ACID에서 'I'에 해당하는 Isolation(격리성)의 의미는?
✅ 정답: ①
격리성(Isolation)은 동시에 여러 트랜잭션이 실행되더라도 서로 간섭하지 않도록 보장하는 속성입니다. 누군가 데이터를 읽는 중에 다른 사람이 데이터를 쓰더라도 읽기 작업이 방해받지 않습니다. ④는 지속성(Durability)에 해당합니다.
4Delta Lake의 Schema Enforcement와 Schema Evolution의 차이로 올바른 것은?
✅ 정답: ④
Schema Enforcement는 기존 스키마와 맞지 않는 데이터가 들어오면 자동으로 거부하는 보호 기능이고, Schema Evolution은 새 컬럼 추가처럼 의도적인 스키마 변경을 허용하는 유연성 기능입니다. 두 기능이 함께 동작해 데이터 품질과 유연성을 동시에 보장합니다.
5Delta Lake에서 모든 변경 이력을 버전별 JSON으로 기록하는 폴더 이름은 무엇인가요?
정답: _delta_log
Delta 테이블 폴더 안에 자동으로 생성되는 디렉터리입니다. INSERT·UPDATE·DELETE·MERGE 등 모든 변경 작업을 버전 번호별 JSON 파일로 기록하며, ACID 트랜잭션과 Time Travel의 핵심 기반이 됩니다.
